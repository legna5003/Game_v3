## v5.1 변경 내역

- 드라이브 인덱싱을 **특정 폴더 구조를 가정하지 않는 설계**로 전면 교체 (3절). 폴더명 대신 파일 내용·캘린더·메일·연동 앱·사진 위치를 단서로 현장을 찾고, 못 찾으면 실시간 검색으로 넘어감

- 온보딩을 점진형으로 변경: 5분 안에 진행 중 현장부터 사용 시작

## 0. 전략 요약

**타깃**: 호주의 1~20인 규모 트레이디·빌더 사업주. 1차 진입은 **한국어를 쓰는 사장님**(타일, 목수, 플라스터, 방수, 빌더 등), 2차는 전체 호주 트레이디.

**왜 한국어 사용 사장님부터인가**
- 고객·공급업체·카운슬·인스펙터와는 영어로 소통해야 하는데, 영어 메일·문자 작성이 가장 큰 사무 부담인 집단이다.
- ServiceM8·Tradify 등 기존 앱은 영어 전용이고 음성 비서가 없다.
- 커뮤니티가 촘촘해 입소문 확산이 빠르고, 파일럿 대상자 확보가 쉽다.
- 여기서 검증한 제품은 언어 설정만 바꾸면 영어권 트레이디에게 그대로 판매된다.

**승부처 3가지**

| 승부처 | 이 시장에서의 의미 | 성공 지표 |
|---|---|---|
| **① 신뢰** | 고객에게 나가는 견적·메일·문자, 특히 **번역된 영어 문장**이 틀리면 안 된다 | 파일럿 오발송·오번역 발송 0건 |
| **② 좁고 깊은 업무** | "주소 하나로 그 현장의 모든 것" + 돈이 새는 곳(변경공사·미수금) | 핵심 업무 음성 완료율 ≥ 90% |
| **③ 연동 용이** | Google 1회 연결로 **어떤 방식으로 정리된 드라이브든** 현장을 인식 + 쓰던 앱 유지 | 5분 안에 사용 시작, 8가지 정리 유형 모두에서 현장 인식 ≥ 90% |

**하지 않을 것**: 잡 관리 앱 신규 개발, 인바운드 전화 접수, 범용 잡담 비서, 도면 축척 추정, 건축 규정 판단.

## 1. 한국어·영어 병행 설계

### 1.1 언어 규칙
| 상황 | 언어 |
|---|---|
| 사장님 ↔ 자비스 대화 | 사장님이 말한 언어로 답변 (한국어로 물으면 한국어, 영어로 물으면 영어). 섞어 말해도 처리 (예: "12 Smith Street 배리에이션 하나 추가해줘") |
| 고객·공급업체·서비에게 나가는 메일·문자 | **수신자 프로필의 언어** (기본 영어, 한국인 서비는 한국어 가능) |
| 들어온 영어 메일·문자 | 사장님 언어로 요약해서 읽어줌, 원문은 화면에 |
| 도면·견적 판독 결과 | 사장님 언어로 설명, 수치·시트번호·품목명은 원문 유지 |

### 1.2 번역 발송의 신뢰 장치 (strict 확장)
한국어로 지시 → 영어로 발송되는 모든 건은 다음 순서를 거친다.
1. Live가 의도 파악 → **Flash가 영어 문장 생성** (업종 톤, 호주식 표현, 고객 이름·주소·금액·날짜는 구조화된 값에서 채움)
2. **Flash가 영어 문장을 다시 한국어로 역번역** → 원래 지시와 의미 비교, 불일치 시 재생성
3. 확인 발화: "Johnson 고객님께 영어로 보냅니다. 내용은 '내일 오전 8시에 도착 예정이며 타일 작업은 이틀 걸립니다'입니다. 보낼까요?" — **핵심 값(이름·주소·금액·날짜·시간)은 영어와 한국어로 모두 복창**
4. 화면에는 실제 발송될 영어 원문 표시 (운전 중이 아닐 때)
5. 발송 후 30초 취소 창

### 1.3 용어집
- 한국 트레이디 현장 용어 ↔ 호주 영어 매핑: 방수 ↔ waterproofing/membrane, 줄눈 ↔ grout, 석고보드 ↔ plasterboard/gyprock, 변경공사 ↔ variation, 준공검사 ↔ final inspection/OC, 서비 ↔ subbie, 전기공 ↔ sparky, 목수 ↔ chippy 등
- 사용자별 사전: 현장 주소·고객·공급업체(Bunnings, Reece, Beaumont Tiles 등)·교외명을 세션에 주입
- 코드 스위칭 평가셋: 한국어 문장 안의 영어 주소·고유명사 인식률을 별도 측정

## 2. 핵심 개체: 프로젝트 = 현장 주소

```
Project
  address        "12 Smith St, Parramatta NSW 2150"   (Google Address Validation API로 정규화)
  aliases        ["Smith St job", "파라마타 리노", "Johnson's place"]
  client         { name, phone, email, language }
  drive_refs     [Drive 파일·폴더 ID 목록]   ← 사용자 폴더를 옮기지 않고 "가상 인덱스"로 연결
  docs           { quotes[], plans[], variations[], invoices[], permits[], photos[], contracts[] }
  plan_index     [ {sheet, title, scale, rev, page, summary, superseded_by} … ]
  status         lead | quoted | won | in_progress | practical_completion | invoiced | closed
  external_ids   { xero_contact, servicem8_job, tradify_job }
  subbies        [ {trade, name, phone, language, insurance_expiry} ]
```

- **주소 해석**: 음성의 주소·별칭·고객 이름을 프로젝트 목록과 퍼지 매칭. 후보 2개 이상이면 선택지 제시. "그 현장"은 세션 내 마지막 프로젝트.
- **사용자 파일은 옮기거나 이름을 바꾸지 않는다.** 자비스는 인덱스만 갖는다. 정리 제안은 사장님이 원할 때만.

## 3. 어떤 드라이브든 현장을 찾아내는 인덱싱 (구조 무관 설계)

### 3.0 설계 원칙
트레이디마다 드라이브 정리 방식이 전부 다르다. 주소별로 정리한 사람, 고객 이름별, 연도별, 문서 종류별(견적 폴더 하나에 전부), 폴더 없이 한곳에 몰아둔 사람, 파일은 거의 없고 Gmail 첨부로만 가진 사람, 빌더가 공유한 공유 드라이브만 쓰는 사람도 있다. 따라서:

1. **폴더 구조를 가정하지 않는다.** 폴더명은 여러 단서 중 하나일 뿐이다.
2. **파일 내용과 다른 서비스의 기록을 단서로 쓴다.** 견적서 안의 현장 주소, 도면 표제란의 주소, 캘린더 일정의 장소, 메일 스레드의 주소, 사진 위치 정보까지 모은다.
3. **인덱스가 틀리거나 비어 있어도 업무가 멈추지 않는다.** 인덱스에서 못 찾으면 실시간 전문 검색으로 넘어간다.
4. **사용자에게 정리를 요구하지 않는다.** 확신이 낮은 것만 묻고, 그 답을 규칙으로 저장해 다시 묻지 않는다.
5. **사용자 파일은 옮기거나 이름을 바꾸지 않는다.** 자비스는 가상 인덱스만 갖는다.

### 3.1 단서(Signal) 수집 — 신뢰도 순
| 순위 | 출처 | 얻는 것 | 비고 |
|---|---|---|---|
| 1 | 연동된 잡 관리·회계 앱 (ServiceM8, Tradify, Xero) | **공식 잡 목록, 현장 주소, 고객, 잡 번호** | 연결한 사용자는 이것이 현장 목록의 기준이 됨 |
| 2 | 파일 내용 | 견적·청구서의 "Site address", 도면 표제란의 주소·프로젝트명·도면번호, 계약서 당사자 | Flash가 첫 1~2페이지만 판독 |
| 3 | 캘린더 | 일정의 장소(location), 제목의 주소·고객명 | 진행 중인 현장 파악에 가장 빠름 |
| 4 | Gmail | 스레드 제목·본문의 주소, 첨부 파일, 발신자(건축가·고객·서비) | 첨부만 있고 드라이브엔 없는 문서도 인덱싱 |
| 5 | 연락처 | 고객 주소 | 고객 ↔ 현장 연결 |
| 6 | 사진 위치 정보 | 촬영 위치 → 역지오코딩 → 주소 | 현장 사진 폴더 자동 연결 |
| 7 | 폴더명·파일명 | 주소, 고객명, 잡 번호, 연도 | 보조 단서 |
| 8 | 공유 관계·동시 위치 | 같은 사람이 공유한 파일, 같은 폴더에 있는 파일, 같은 날 수정된 파일 묶음 | 다른 단서를 보강 |

### 3.2 현장 식별 키 — 주소가 없어도 된다
현장은 주소로 부르는 경우가 많지만 항상 그렇지는 않다. 다음 중 하나 이상이면 현장으로 인정한다.
- 정규화된 주소 (Google Address Validation)
- 잡 번호 (J-1043, Q-2026-041 등, 연동 앱 번호 포함)
- 고객 이름 + 기간 (같은 고객의 다른 공사는 기간으로 구분)
- 상업 현장 이름 ("Westfield Parramatta fit-out", "Unit 4 King St")

### 3.3 현장 묶기 (Entity Resolution)
1. 파일·메일·일정마다 단서를 추출해 후보 키(주소·잡 번호·고객·현장명)를 붙인다.
2. 키가 같거나 유사한 항목, 같은 폴더·같은 메일 스레드·같은 공유자로 이어진 항목을 그래프로 연결한다.
3. 연결된 묶음을 현장 후보로 만들고 **신뢰도 점수**를 매긴다 (단서 순위와 개수 기반).
4. 높은 신뢰도는 자동 확정, 중간은 온보딩 확인 목록에, 낮은 것은 "미분류함"에 둔다.
5. 연동 앱이 있으면 그 잡 목록에 우선 매칭하고, 매칭되지 않는 묶음만 새 현장 후보로 제시한다.

### 3.4 정리 방식별 처리 (테스트 기준이 되는 유형)
| 유형 | 예시 | 주로 쓰는 단서 |
|---|---|---|
| A. 주소별 폴더 | `/Jobs/12 Smith St/` | 폴더명 + 파일 내용 |
| B. 고객별 폴더 | `/Clients/Johnson/` | 고객명 + 파일 내용의 주소 (한 고객 여러 현장 분리) |
| C. 연도·월별 | `/2025/March/` | 파일 내용·캘린더·메일 |
| D. 문서 종류별 | `/Quotes/`, `/Plans/`, `/Invoices/` | 파일 내용의 주소·잡 번호로 현장 간 연결 |
| E. 정리 안 함 | 루트에 수천 개, 파일명 `Scan_0042.pdf` | 파일 내용 + 수정일 + 메일 첨부 일치 |
| F. Gmail 중심 | 드라이브 거의 없음 | 메일 첨부·스레드 |
| G. 공유 드라이브·공유받은 파일 | 빌더·건축가가 공유한 도면 폴더 | 공유자 + 도면 표제란 |
| H. 혼합 | 위 유형이 섞임 | 전부 |

### 3.5 점진적 온보딩 — 기다리게 하지 않는다
| 시점 | 처리 | 사용자 경험 |
|---|---|---|
| 연결 직후 ~5분 | 최근 90일 캘린더·메일·수정 파일로 **진행 중 현장만** 먼저 찾기 | "진행 중인 현장 8곳을 찾았어요. 맞나요?" → 바로 사용 시작 |
| 첫 1시간 | 전체 메타데이터 수집, 파일 내용 단서 추출(백그라운드) | 사용 중에도 계속 늘어남 |
| 첫 24시간 | 전체 현장 묶기, 확인 필요 목록 생성 | 저녁에 "확인할 게 12개 있어요" 한 번만 |
| 이후 | 변경분만 처리 (Drive Changes, Gmail 푸시) | 새 파일은 몇 분 내 반영 |

확인 질문은 음성으로도 답할 수 있게 짧게 묶는다: "Scan_0042부터 0051까지 10개가 Smith St 견적 같아요. 맞아요?"

### 3.6 인덱스에 없을 때 — 실시간 검색 폴백
"King St 도면 줘"가 인덱스에서 안 나오면:
1. 드라이브 전문 검색(파일 내용 포함)과 Gmail 첨부 검색을 바로 실행
2. 찾으면 답하고, 그 파일을 해당 현장에 연결 ("앞으로 King St로 기억할게요")
3. 못 찾으면 "드라이브와 메일에서 찾지 못했어요"라고 정확히 말한다. 추측해서 다른 파일을 주지 않는다.

### 3.7 학습 — 고칠수록 좋아진다
- **사용자별 규칙**: 사장님이 고친 내용을 규칙으로 저장 ("이 사람은 `Job-번호` 폴더 = 현장", "Dave Smith는 고객이 아니라 서비").
- **전체 사용자 공통 개선**: 파일 내용은 공유하지 않고, 어떤 단서 조합이 맞았는지 통계만(사용자 동의 하) 모아 기본 규칙과 점수 가중치를 개선한다. 사용자가 늘수록 신규 사용자의 첫 인식률이 올라간다.

### 3.8 검색 방식 (하이브리드)
1. 현장 필터(주소·별칭·잡 번호·고객) → 2. 문서 유형 필터 → 3. 최신성(최신 리비전) → 4. 필요할 때만 의미 검색(임베딩) → 5. 그래도 없으면 실시간 폴백(3.6)
- 저장소: Firestore(메타·인덱스·단서 그래프) + 벡터 검색. 사용자별로 완전히 분리된 인덱스.

### 3.9 도면 리비전 관리
- 같은 도면번호의 여러 리비전을 묶고, 최신이 아닌 것은 `superseded`로 표시
- 오래된 리비전이 더 최근에 수정된 경우 경고
- "리비전 B랑 C 뭐가 달라?" → Pro가 두 시트 비교

### 3.10 심층 인덱스 범위와 비용 (2차 출처 단가 기준 추정, 사용자 1인)
| 단계 | 대상 | 일회성 비용 (AUD) |
|---|---|---|
| 메타데이터 + 단서 추출 | 전체 파일·메일 첨부 (2만 개 기준, 첫 1~2페이지만) | 10~25 |
| 심층 인덱스 | 진행 중·최근 12개월 현장의 도면 시트·견적 항목·임베딩 | 30~60 |
| 나머지 오래된 현장 | 질문할 때 지연 처리 | 사용량에 따라 |
| 증분 동기화 | 변경분 | 월 2~5 |

### 3.11 다른 저장소
Google 드라이브 외에 OneDrive·Dropbox를 쓰는 트레이디도 있다. 인덱서는 저장소 어댑터 구조로 만들어 P5에 추가한다. 단서 추출·현장 묶기·검색 로직은 저장소와 무관하게 재사용된다.

## 4. 핵심 업무 (우선순위순)

등급: `auto` 즉시 / `confirm` 1회 확인 / `strict` 고정 템플릿 복창 + 명시적 승인 + 30초 취소

### 4.1 견적 (Quote)
| 요청 예시 | 동작 | 등급 |
|---|---|---|
| "12 Smith St 견적 읽어줘" | 인덱스에서 최신 견적 → 총액·GST·주요 항목·유효기간 요약 | auto |
| "그 견적 고객한테 보내줘" | 고객 확정 → 영어 메일(번역 장치 적용) + PDF 첨부 → 복창 → 발송 | strict |
| "그 현장 견적 보여줘" | 휴대폰 화면에 PDF 표시 | auto |
| "견적 보낸 지 일주일 넘은 거 있어?" | 미응답 견적 목록 → "후속 문자 보낼까요?" | auto → strict |
| "Smith St 견적 승인됐어" | 상태 → won, 연동 앱에 잡 생성 | confirm |

견적 작성은 연동된 앱(ServiceM8·Tradify·Xero)에서. 연동이 없을 때만 Docs 템플릿 → PDF.

### 4.2 도면 (Plans)
| 요청 예시 | 동작 | 등급 |
|---|---|---|
| "Smith St 도면 올려줘" (파일·사진·메일 첨부) | 현장 폴더에 저장 → 시트별 인덱싱 → "시트 12장, 리비전 C" | confirm |
| "1층 평면도 보여줘" | 최신 리비전 시트를 화면에 표시 + 요약 | auto |
| "주방 창문 사이즈 확인해줘" | Pro가 해당 시트 판독 → 창문 스케줄·치수선의 **표기값** 답변 + 해당 영역 확대 표시 | auto |
| "욕실 방수 범위 어떻게 돼 있어?" | 시트 + 스펙 노트 판독 → 표기된 내용만 답변 | auto |
| "도면 타일러한테 보내줘" | 서비 확정 → 해당 시트 첨부 메일/문자 → 복창 | strict |

**판독 원칙**
- 도면에 **적힌 값만** 읽는다. 적혀 있지 않으면 "도면에 치수가 표기돼 있지 않아요"라고 답하고 추정하지 않는다.
- 모든 답변에 출처(시트 번호·리비전)를 붙이고, 신뢰도가 낮으면 "화면으로 직접 확인해 주세요"로 유도한다.
- 구조·전기·방수 규정 적합성 판단은 하지 않는다.
- 답변 형식: `{answer, sheet, revision, region_bbox, source_text, confidence}`

### 4.3 변경공사 (Variation) — 신규
| 요청 예시 | 동작 | 등급 |
|---|---|---|
| "Smith St 배리에이션 추가: 파워포인트 2개 추가, 380불" | 변경공사 기록 생성 (내용·금액·GST·일정 영향) → 영어 변경공사 서류 PDF | confirm |
| "그거 고객한테 승인 받아줘" | 고객에게 서명·승인 링크 메일/문자 → 복창 | strict |
| "Smith St 승인 안 된 배리에이션 있어?" | 미승인 목록 + 금액 합계 | auto |
| 승인 완료 시 | "Johnson 고객님이 380불 변경공사를 승인했어요" 선제 알림, Xero 청구 항목에 반영 제안 | confirm |

- 승인 링크는 간단한 웹 페이지(이름 입력 + 동의 체크 + 타임스탬프·IP 기록). 전자서명 서비스 연동은 P4.
- 주별 주택건축 규정(서면 계약·서면 변경공사 요건)은 주마다 다르므로 서류 템플릿은 주별로 검토 후 제공하고, 법률 자문이 아님을 명시.

### 4.4 돈: 미수금·청구 (Xero) — P2로 앞당김
| 요청 예시 | 동작 | 등급 |
|---|---|---|
| "누가 나한테 돈 안 줬어?" | Xero 미수 청구서 목록·연체일·합계 | auto |
| "Smith St 2차 진행 청구서 보내줘" | Xero 초안 청구서 생성 → 금액 복창 → 발송 | strict |
| "Johnson한테 연체 독촉 문자 보내줘" | 정중한 영어 독촉 문자(번역 장치) → 복창 | strict |
| 매주 월요일 | "연체 3건, 합계 1만 2천 불" 브리핑 | — |

### 4.5 메일·문자
| 요청 예시 | 동작 | 등급 |
|---|---|---|
| "오늘 온 메일 중 중요한 거 읽어줘" | 고객/공급업체/카운슬/청구/광고 분류 → 한국어 요약 | auto |
| "Johnson한테 내일 8시 도착한다고 문자해" | 번역 장치 → 복창 → 발송 | strict |
| "Reece에 PO 보내면서 도면 첨부해" | 공급업체 메일 + 인덱스의 최신 도면 첨부 | strict |
| "답장 초안 써놔" | Gmail 초안 저장 | confirm |
| 새 문의 메일 도착 | "새 견적 문의예요, 15 King St 욕실 리노. 리드로 등록할까요?" | confirm |

SMS는 호주 전용 번호(long code)로 발송하고 회신도 같은 번호로 받아 보고. 알파 태그(회사명 발신)를 원하면 ACMA Sender ID 등록 지원.

### 4.6 일정·서비 조율
| 요청 예시 | 동작 | 등급 |
|---|---|---|
| "내일 오전 Smith St 2시간 잡아줘" | 겹침·이동시간 확인 → 등록 | confirm |
| "목요일 Smith St에 전기공 불러줘" | 서비 목록에서 sparky 선택 → 일정 문자 발송 → 회신 대기 → "Dave가 목요일 7시 OK했어요" | strict |
| "비 오면 콘크리트 타설 미뤄야 하는데 금요일 날씨 어때?" | 기상청(BOM) 예보 조회 | auto |
| "다음 현장 어디야?" | 다음 일정 + 출발 시간 | auto |

### 4.7 아침 브리핑·선제 알림 — 신규
매일 아침 설정 시간(예: 6:00)에 출발 전 음성 브리핑:
- 오늘 현장 일정과 이동 순서
- 날씨 경고 (비·강풍·폭염: 외부 작업·타설·지붕 작업 영향)
- 미응답 견적 후속, 미승인 변경공사, 연체 미수금
- 만료 임박 서류 (보험·라이선스·서비 보험증명)
- 어제 들어온 중요한 메일·문자

### 4.8 현장 기록
| 요청 예시 | 동작 | 등급 |
|---|---|---|
| "사진 찍어서 Smith St에 저장해, 방수 완료" | 현장 사진 폴더 + 캡션 + 날짜·위치 | auto |
| "오늘 일지: 방수 끝, 내일 타일 시작, 비 때문에 두 시간 늦음" | 현장 일지(날씨·인원 자동 기록) | auto |
| "고객한테 진행 상황 보내줘" | 일지 + 사진 2~3장으로 영어 진행 보고 | strict |

현장 일지는 분쟁·지연 클레임 때 증거가 된다.

### 4.9 서류 만료 관리 — 신규 (P3)
- 사장님 라이선스, 공공배상책임보험, 산재보험, 차량 보험, 서비 보험증명 만료일을 메일 첨부·드라이브에서 추출
- 30일·7일 전 알림, 서비에게 갱신 증명 요청 문자 (strict)

### 업무 확장 기준 (유지)
주 3회 이상 반복 · 손으로 3분 이상 · 음성이 편한 상황 · 되돌리기 가능 — 4개 모두 만족 시에만 추가.

## 5. 신뢰 설계

| 등급 | 대상 | 규칙 |
|---|---|---|
| `auto` | 조회, 읽기, 내부 저장(사진·일지) | 즉시 실행 |
| `confirm` | 일정 생성, 리드·변경공사 기록, 초안 저장, 파일 업로드 | 요약 후 "할까요?" 1회 |
| `strict` | 고객·서비·공급업체에게 **나가는 모든 것**, 청구서 발송, 삭제, 외부 앱 쓰기 | 서버 고정 템플릿으로 수신자·주소·금액·날짜 복창(번역 건은 영·한 병기), 명시적 긍정만 허용, 10초 무응답 취소, 30초 취소 창 |

- 등급은 **서버 정책 엔진이 강제**한다. 모델이 도구를 호출해도 확인 토큰 없이는 실행되지 않는다.
- 유사 이름(Johnson/Johnston, 김영수/김영숙) 선택지 강제, 사전에 없는 새 수신자는 화면 확인 필수.
- 영구 삭제 도구 없음, 사용자 드라이브 파일 이동·이름 변경 없음.
- 감사 로그 + 저녁 요약: 매일 17:30 "오늘 자비스가 한 일" (번역 발송 건은 영어 원문 포함).

```
│  단서 수집(드라이브·메일·캘린더·연동 앱·사진) → 현장 묶기 → 심층(도면·견적·임베딩)   │
│  Drive Changes 푸시 → 증분 재처리                                            │
└──────────────────────────────────────────────────────────────────────────┘
   Firestore(프로젝트·인덱스·사전)  Vector Search(임베딩)  Cloud SQL(감사로그)  Secret Manager(OAuth)
```

- Live 세션: 압축·재개 항상 켜기, 55분 선제 재접속.
- Live에는 문서 원본을 넣지 않는다(컨텍스트 약 128K). 인덱스 검색 결과와 서브에이전트 요약만 전달.
- 데이터는 호주 리전, 사용자 원본 파일은 사용자 드라이브에만 존재.

## 9. Google 권한·보안 심사 (신규 핵심 리스크)

- 수백 현장의 기존 파일을 읽으려면 **Drive 전체 읽기 권한**이 필요하고, 이는 Google **제한(restricted) 스코프**다. Gmail 읽기도 제한·민감 스코프에 해당한다.
- 외부 사용자에게 출시하려면 **CASA 보안 평가**(Google 지정 제3자 평가기관)를 통과해야 하고, **매년 재평가**가 필요하다. 비용 추정치는 출처마다 크게 다르다(수천~수만 달러).
- 대응
  - 사내·파일럿 단계: Workspace 내부 앱 또는 테스트 사용자(100명 한도)로 운영 → 심사 없이 검증 가능
  - P3 시작과 동시에 CASA 준비(보안 정책, 침투 테스트, 데이터 처리 문서화)
  - 최소 권한: Calendar·Contacts는 필요한 범위만, 발송은 `gmail.send` 분리
  - 대안 검토: 사용자가 Google Picker로 "현장 최상위 폴더"만 선택하게 하는 방식이 제한 스코프를 피할 수 있는지 P0에서 검증

## 15. 첫 2주 할 일

1. GCP 프로젝트(au-southeast1), Drive·Gmail·Calendar·Contacts·Address Validation API, 내부용 OAuth(테스트 사용자)
2. **8가지 정리 유형별 테스트 드라이브 구축** (견적·도면·청구서·사진 샘플을 유형별로 배치, 일부는 파일명을 `Scan_0042.pdf`처럼 무의미하게) → 단서 추출·현장 묶기 정확도를 유형별로 측정 (가장 먼저 검증할 가정)
3. 프로젝트 리졸버(주소·별칭·한국어 별칭 퍼지 매칭)
4. 정책 엔진 골격: 등급 테이블, strict 템플릿(영·한), 확인 토큰, 30초 큐, 감사 로그
5. 번역 발송 장치 프로토타입 + 한국어 지시 30개 원어민 검수
6. ADK `LlmAgent(model="gemini-3.8-live")` + 도구 6개: `find_project`, `quote_read`, `quote_send`, `gmail_summary`, `sms_send`, `calendar_create`
7. 파일럿 후보 한국어 사용 트레이디 10명 섭외 — **업종(빌더·타일·전기 등)과 드라이브 정리 방식이 서로 다르게** 모집, 도면 샘플 10세트 확보
8. Google Picker 폴더 선택 방식으로 제한 스코프 회피 가능한지 확인
